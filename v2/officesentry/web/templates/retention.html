Data retention

How long Office Sentry keeps personal data about your clients' staff and your own team. The worker applies these settings once a day, deleting in small batches. Deleted rows are overwritten in the database file where that costs nothing extra; backups keep them until they rotate.

Snapshots

Everything a collection read: every user, mailbox, device, policy and group, with names and addresses. Reports, the change history and each person's page read them. Trend numbers (counts only) are kept forever.

The latest snapshot and anything collected in the last 24 hours are always kept.

{{ next_run(counts.snapshots, 'older snapshot') }}

Daily history

The same data as the snapshots, but each user, mailbox, device and policy is stored once, and again only when it changes, so a client can be shown as it was on any day. It takes far less room than a snapshot a day. It starts with the snapshots already kept, so on the day it's turned on it reaches back as far as they do.

{{ number('state_months', p.state_months, d.state_months, 'Keep forever', unit='Months', label='Keep for') }}

The latest state of each client and data source is always kept. Sign-in detail isn't part of it; the full sign-in log is kept under Activity history below.

{{ next_run(counts.state_months, 'older collection') }}

Sign-in detail

From the Entra sign-in log: who signed in, from which IP addresses, countries and cities, which apps, failed and risky sign-ins, and legacy-protocol sign-ins. By default it's kept as long as the snapshot it's in, which is about 13 months for monthly snapshots. The full sign-in log is kept separately, under Activity history below.

{{ number('signin_days', p.signin_days, 90, 'Keep as long as its snapshot') }}

At least 30 days, so the sign-in reports always have last night's data. After this, older snapshots still have everything else.

{{ next_run(counts.signin_days, 'sign-in row') }}

Activity history

Every sign-in and directory audit event Office Sentry has read from each client's logs, kept beyond the 30 days Microsoft keeps them: who signed in, when, from which address, country and app, and every admin change in Entra ID. Each client's Activity history page, each person's page and the Admin activity report read it. It's stored in monthly files beside the database, and a month older than its period is deleted as a whole.

Resolved findings

Findings that were fixed: the check, the account or object it named and when it was first seen, last seen and resolved. Open findings and accepted risks are never deleted. Each client's findings from its first scan are kept, so alert emails can still tell them apart.

{{ number('findings_days', p.findings_days, 365, 'Keep forever') }}

Counted from the day a finding was resolved. If it comes back after it's been deleted, it shows as new.

{{ next_run(counts.findings_days, 'resolved finding') }}

Run logs

The progress lines of each collection, which can name accounts and sites. Warnings and errors are always kept, so a run's page still says why it failed.

{{ number('run_log_days', p.run_log_days, d.run_log_days, 'Keep forever') }} {{ next_run(counts.run_log_days, 'log line') }}

Activity log

Who signed in to the portal and changed what, with the address they came from. Failed and slowed-down sign-ins are always removed after 90 days.

{{ number('audit_days', p.audit_days, 365 * 2, 'Keep forever') }}

Never less than {{ audit_floor|plural('day') }}: the log is how you find out who changed a setting, opened a client's data or signed in from somewhere unexpected, and security reviews and investigations usually look back at least a year.

{{ next_run(counts.audit_days, 'entry') }}

Issued reports

The exact PDF and spreadsheet files sent or approved for clients (Report history), with their recipients.

{{ number('issued_days', p.issued_days, 365 * 3, 'Keep forever') }}

Never less than {{ issued_floor|plural('day') }}, and the latest file of each report for each client is always kept, because month-end reporting compares against it.

{{ next_run(counts.issued_days, 'issued report') }}

Changes are recorded in the activity log. Shortening a period deletes data at the next daily pass, and it can't be brought back except from a backup.
